Statewide Parcel Data ETL Pipeline

Automated Python procedure for statewide parcel data extraction, cleaning, and standardization.

Role
Data Scientist  ·  GIS Analyst
Client / Context
CDM Smith Inc.  ·  Columbus, OH

The Challenge

Turning raw parcel records for an entire state into clean, consistently classified, audited data is a heavy data engineering problem, especially at the scale of every parcel in Ohio. Parcel data comes from many counties, each often digitized under different local conventions, land use coding standards, or geometry states, including multipart polygons, near duplicate records, and overlapping boundaries left over from data conflation. At statewide scale, millions of records, anything that isn't a well optimized spatial join or transform becomes painfully slow. Classification logic also can't live buried in code: as categories or business rules evolve, hardcoded mapping dictionaries become a liability, since every correction requires a code change and a redeploy. And data quality varies widely by county, so a single statewide quality bar doesn't work. Quality needs to be assessed county by county before deciding how much to trust that county's data, and nothing should silently ship bad data once it's ready to go out the door.

Solution

I designed and built this as a modular pipeline of ArcGIS Python Toolboxes and standalone Python scripts, each tool owning one clearly scoped stage, so the whole pipeline can run end to end or be re-run at just the stage that needs it. It covers everything from initial data acquisition through cleaning, quality auditing, spatial assignment, classification, aggregation, and a final validation gate before export. I designed and built this solo, as part of the same statewide automation effort as the terrain preprocessing tools.

Method

The pipeline moves parcels through six stages, each with its own tool, so the whole thing runs end to end or a single stage can be re-run on its own when something needs fixing.

Configuration and acquisition

Every session starts by syncing version-controlled CSV configuration files (classification rules, county quality tiers, validation thresholds) into the geodatabase, so a rule change is a one-line CSV edit rather than a script change and redeploy. Parcel data itself is then pulled directly from a statewide parcel feature service, with a built-in test mode that lets an analyst validate the connection or inspect a schema against a small sample without ever touching the production dataset the rest of the pipeline reads from.

Cleaning and quality auditing

Raw parcels run through a configurable cleaning sequence: multipart polygons are exploded to single part, geometric duplicates are identified and removed, and overlapping records above a configurable similarity threshold are resolved down to a single kept record with a defined tie break rule. Every deleted record is preserved in a scratch database for audit and recovery rather than thrown away silently. Before classification, every county's data is then scored on measurable quality metrics and handed to an analyst for review. This is enforced as a hard gate: classification will not run until every county has been reviewed and approved.

Spatial assignment at scale

Assigning every parcel to its containing spatial zone is normally the most expensive step in a pipeline like this. I rebuilt it using OGR and GEOS with a process pool, splitting the zones across worker processes that each run their own spatial index lookups and write results to local staging files that get merged back at the end. That took the join from a multi-hour operation down to roughly half an hour.

Classification and aggregation

Every parcel gets classified against the same configuration table used at sync time, so classification logic and configuration live in exactly one place. For industrial parcels specifically, whether a code should be treated as heavy or light industrial is decided from actual employment data overlaid onto those parcels rather than an assumption, with a documented fallback for the rare case with no data available. Classified parcel-level data is then pivoted up into zone-level summary tables for downstream use.

Validation and export

Before a final export, every result is checked against a set of validation rules covering internal consistency, statewide ratio sanity bounds, and comparisons against a prior baseline where one exists. Any error-level failure halts the export outright, and any warning requires an analyst to explicitly acknowledge it before the pipeline will proceed, so nothing ships without a human reviewing the exceptions.

Technical Highlights

  • Language / Platform: Python, ArcGIS Pro (arcpy) Python Toolboxes, plus standalone Python scripts for performance critical stages
  • Data acquisition: REST feature service integration, with a safe test mode isolated from production data
  • Geometry processing: Multipart to single part explosion, geometric and overlap based deduplication with configurable thresholds, geodesic area calculation
  • Performance engineering: A parallelized spatial join using OGR/GEOS and a process pool, cutting a statewide spatial join from hours down to roughly 30 minutes
  • Data governance: Config driven business rules stored in version controlled CSVs, county level quality tiering, and analyst approval gates enforced in code before downstream stages can run
  • Quality assurance: Per county and per zone audit tables, a rules driven validation stage with error and warning severities, and a hard gate before any final export

Outcome

A pipeline like this only earns trust if every number in the final export can be traced back to a defensible decision, whether that's a config driven classification rule, an analyst approved data quality tier, or a validation check that passed.

  • Governance gates are built directly into the pipeline rather than relying on someone remembering to check things manually, so bad data gets caught and reviewed before it reaches a deliverable.
  • Every classification decision stays auditable and easy to correct through a configuration edit, without touching code.
  • The parallelized spatial join turned the pipeline's most expensive step from a multi-hour run into something that fits comfortably inside a normal working session.
