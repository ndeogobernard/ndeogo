SSURGO Soil & Slope Classifier

ArcPy automation classifying parcel records by SSURGO slope parameters.

Role
Data Scientist  ·  GIS Analyst
Client / Context
CDM Smith Inc.  ·  Columbus, OH

The Challenge

Land use models that classify terrain for transportation and infrastructure planning need accurate slope data derived from soil survey information. That data comes from the USDA's SSURGO (Soil Survey Geographic Database), county by county, and getting it into a usable state is normally a slow, manual, and error prone process.

  • Publication dates for each county's soil data change over time, so URLs can't be hardcoded. A stale link either fails outright or silently returns an outdated dataset.
  • Downloads can fail partway through or return HTML error pages instead of real data, and nothing catches that until it breaks a downstream step.
  • A statewide run touches 88 separate counties. If it fails on county 60, there's no way to resume without starting over.
  • The raw output needs to be classified into meaningful terrain categories (Level, Moderate, Steep) and checked for data quality before anyone downstream can trust it.

The tool needed to turn a manual, single county workflow into a reliable, auditable, statewide (or district or county scoped) batch process that a GIS analyst could kick off and walk away from.

Solution

I built this as a custom ArcGIS Python Toolbox (.pyt), so it plugs directly into ArcGIS Pro as a native geoprocessing tool with a proper parameter UI, no separate script execution required. I built this solo, as part of a larger GIS automation pipeline supporting a statewide land use model.

Method

The tool walks each county through the same sequence, with enough validation built in to run unattended across the whole state.

Finding the right data

Rather than pointing at fixed download URLs, the tool uses dynamic data sourcing: it queries USDA's Soil Data Access API at runtime to get each county's current publication date, then builds the download URL from that, warning the operator clearly if the API is unreachable rather than failing silently. On top of that sits defense in depth on downloads, every zip is checked for a minimum file size and a valid zip header before being trusted, which catches the common failure mode where a server quietly returns a small HTML error page with a .zip extension. If a folder of pre downloaded zips is supplied, the tool checks there first.

Picking up where it left off

Processing 88 counties takes time and can fail midway (a network blip, bad data, and so on). Rather than treating a statewide run as all or nothing, the tool checkpoints each county: counties that already have output on disk are skipped by default (with an explicit override flag), so a failed run can simply be relaunched and pick up where it stopped instead of starting over.

Extracting and classifying slope

Slope values use a two tier fallback: pulled directly from the SDA API first (faster, no need to parse tabular files), with automatic fallback to parsing the raw muaggatt.txt file from the extracted survey package if the API is unavailable. Either path feeds the same classification logic, where each map unit is sorted into Level, Moderate, and Steep bands against thresholds exposed as configurable tool parameters (defaulting to project standard values) rather than buried as magic numbers, so analysts can adjust them without touching code.

Checking the work

Before anything runs, the tool validates its own prerequisites (for example, that the required base layer exists and is populated), so failures produce a clear message instead of a cryptic stack trace deep into a long run. Once processing starts, each county's result is automatically flagged (PASS, WARN_HIGH_NODATA, WARN_LOW_COVERAGE, SKIPPED, or FAILED) based on data coverage thresholds, and every run closes out with a pipe delimited QAQC report and a map unit level detail CSV, formatted for both human review and direct database import.

Technical Highlights

  • Language / Platform: Python, ArcGIS Pro (arcpy) Python Toolbox
  • Integration: USDA Soil Data Access REST API (JSON queries), USDA Web Soil Survey download service
  • Data handling: Shapefile processing, cursor based field updates, feature class merging, geodatabase I/O
  • Reliability engineering: API first with file based fallback, download integrity validation, resumable batch processing, upfront input validation
  • Scope flexibility: Supports statewide, ODOT district, and single county runs from the same tool via a built in county to district mapping for all 88 Ohio counties

Outcome

This tool turns a data acquisition step that would otherwise require someone manually tracking 88 counties' worth of download links, file integrity, and slope classification into a single, self auditing, restartable geoprocessing run that an analyst can launch statewide and trust without babysitting.

  • Data quality issues are caught automatically at the source instead of surfacing several pipeline stages later, once bad data has already spread downstream.
  • The QAQC report and map unit CSV leave a paper trail for every run, useful for supervisor review, database import, and personal audit.
  • Slope thresholds are parameters rather than hardcoded values, so the classification logic can be retuned for a new methodology without touching the code.

That matters most when the output feeds a statewide land use model that other decisions depend on.
