EPA Water Boundary Delineator

Automated spatial boundary delineation for Ohio public water systems.

Role
Data Scientist  ·  GIS Analyst
Client / Context
CDM Smith Inc.  ·  Columbus, OH

The Challenge

A statewide land use model needed to know, for every parcel in Ohio, whether it sits inside a public water service area, which drives the with water versus without water classification downstream. The source for that is the EPA's Community Water System service area dataset, but turning it into something usable for a single state runs into real obstacles. The dataset ships as a large GeoPackage containing every state's data, not just Ohio's, so pulling only what's relevant means filtering by the right field rather than clipping geographically after the fact. Community water systems aren't the whole picture either, the EPA separately tracks non-community systems that need to be merged in rather than ignored, and some projects also have a locally supplied private sewer boundary that needs to fold into the same output. On top of that, boundaries from different sources overlap in places, and overlapping polygons would double count coverage further downstream.

Solution

I built this as a custom ArcGIS Python Toolbox (.pyt), consistent with the rest of this pipeline, so it runs as a native ArcGIS Pro geoprocessing tool. It downloads and caches the EPA data, filters it to Ohio, merges in an optional local sewer layer, clips and dissolves to the selected scope, and writes a clean water service boundary straight into the project geodatabase. I built this solo, as part of the same statewide land use automation pipeline as the slope and floodplain preprocessing tools.

Method

The tool moves from data acquisition to a clean output boundary in a sequence of clearly separated steps, each guarding against a specific way the process could go wrong.

Getting the data, once

The tool checks for a locally cached copy of the EPA GeoPackage first. Only if it's missing does it download the zip from GitHub, extract just the GeoPackage from inside it, and discard the rest, so every later run skips the download entirely. Rather than pulling every state's data and clipping it down afterward, the Community Water System and non-community system layers are filtered directly by their Ohio specific attribute fields at read time, so only relevant records ever get processed.

Merging every relevant source

The Ohio filtered CWS and T_NTNC layers are merged together, and if a private or local sewer boundary shapefile is supplied, it gets folded into the same merge. If none is provided, the tool proceeds cleanly with just the two EPA layers rather than requiring one. The clip boundary itself is built from the project's TAZ polygons for whichever scope is selected (statewide, an ODOT district, a single county, or a multi county selection), and the merged water layer is clipped to it.

Resolving overlap

Boundaries from different sources and different systems overlap each other in places, so after clipping, everything is dissolved into a single clean layer, meaning the same physical coverage never gets represented by multiple stacked polygons. Every polygon in the final output then gets a simple Has_Water = 1 flag. Downstream, any parcel that doesn't spatially intersect one of these polygons is treated as Has_Water = 0, keeping the flag logic explicit rather than ambiguous.

Checking the work

Before anything runs, the tool validates its own prerequisites, so a missing layer produces a clear message instead of a cryptic failure deep into a long run. After processing, it checks the output for red flags such as zero features after clipping, zero records from either EPA layer, or a suspiciously small output polygon count, and raises clear warnings rather than staying silent. Every run closes out with a QAQC log covering per layer record counts at each stage.

Technical Highlights

  • Language / Platform: Python, ArcGIS Pro (arcpy) Python Toolbox
  • Data source: EPA Community Water System Service Area Boundaries (v3.0), via the EPA ORD GitHub repository, delivered as a GeoPackage
  • Networking: Streamed download with progress logging, SSL handling for corporate network compatibility, local caching to avoid redundant downloads
  • Geoprocessing: Attribute filtered layer reads from a GeoPackage, feature merge including an optional user supplied layer, clip to a dissolved TAZ boundary, dissolve to resolve overlap, feature class export to geodatabase
  • Scope flexibility: Statewide, ODOT district, county, and multi county processing from a single tool

Outcome

Whether a parcel has water service access is a direct input into how it gets classified in the larger land use model, so an incomplete or double counted water layer would quietly distort that classification for however many parcels it touches.

  • Filtering to Ohio at the source, rather than clipping a nationwide dataset after the fact, keeps every processing step working with only the relevant records.
  • Merging in every relevant layer, including an optional locally supplied one, means the water classification reflects the full picture rather than just the EPA's community water system data alone.
  • Dissolving away overlap before the boundary reaches downstream steps means coverage is represented once, not several times over.

The classification each parcel receives reflects the actual data on the ground, not an artifact of how the source layers happened to be assembled.
