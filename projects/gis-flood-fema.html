FEMA Floodplain Extraction Pipeline

Scripted spatial extraction pipeline for 100-year floodplain data.

Role
Data Scientist  ·  GIS Analyst
Client / Context
CDM Smith Inc.  ·  Columbus, OH

The Challenge

A statewide land use model needed floodplain classification for every parcel in Ohio, sourced from FEMA's National Flood Hazard Layer. Floodplain status takes precedence over every other terrain factor downstream, so getting this step wrong or leaving it stale corrupts everything built on top of it. In practice, pulling this data reliably runs into several problems at once. FEMA doesn't publish Ohio's NFHL at a fixed URL, the effective date shifts over time with no index to just ask what's current. The download also sits behind infrastructure that isn't friendly to automated requests: proxy configurations and SSL interception common on managed networks can silently break a naive request, and a firewall can intercept a blocked download and return an HTML page with a 200 OK status instead of an error, which a script checking only the status code would happily accept as success.

Solution

I built this as a custom ArcGIS Python Toolbox (.pyt), matching the pattern used across this pipeline, so it runs as a native ArcGIS Pro geoprocessing tool with a standard parameter form. It auto discovers and downloads the current FEMA NFHL data, classifies every flood hazard polygon, clips and dissolves to the selected scope, and writes the result straight into the project geodatabase. I built this solo, as part of the same statewide land use automation pipeline as the slope preprocessing tool.

Method

The tool walks through discovery, download, classification, and output in sequence, with enough validation and safety checks to run unattended.

Finding the current data

Since FEMA doesn't expose a current version endpoint, the tool uses date walking: it steps backward from today, day by day, issuing lightweight HEAD requests against the predictable NFHL_39_{YYYYMMDD}.zip naming pattern until it finds one that exists and is a realistic size, probing up to 120 days back to comfortably cover FEMA's actual publication cadence. Once a GDB has been downloaded and extracted, the tool caches it locally and skips the download step entirely on later runs.

Downloading through a hostile network

The download session is built specifically for the network it runs on, not as generic defensive boilerplate. It disables inheriting the system proxy, turns off SSL verification to tolerate the network's SSL re-signing, and sends a real Chrome user agent so it isn't blocked as a bot. Every downloaded file is then checked for a valid zip header and confirmed as a real archive before it's trusted, which catches the case where a firewall silently swaps the real file for an HTML block page while still returning a success status.

Classifying and clipping

Flood classification runs off a single field: SFHA_TF true becomes In_Flood equals 1, false becomes In_Flood equals 0, which cleanly collapses FEMA's more granular zone codes into the binary flag the rest of the pipeline needs. The tool then builds a clip boundary from the pipeline's TAZ polygons for whatever scope is selected (statewide, an ODOT district, or a single county), clips the flood layer to it, and dissolves by flood class so overlapping FEMA zone boundaries collapse into clean, non overlapping polygons.

Checking the work

Before anything runs, the tool validates its own prerequisites, so a missing layer produces a clear message instead of a cryptic failure deep into a long run. After processing, it checks the output against a handful of sanity thresholds (zero features after clipping, zero floodplain polygons, or suspiciously high floodplain coverage) and raises explicit warnings when something looks off, rather than silently producing questionable output. Every run closes out with a detailed QAQC log covering feature counts at each stage and a full FEMA zone breakdown.

Technical Highlights

  • Language / Platform: Python, ArcGIS Pro (arcpy) Python Toolbox
  • Data source: FEMA National Flood Hazard Layer, Ohio statewide file geodatabase
  • Networking: Custom requests session tuned for a restrictive corporate network (proxy bypass, SSL handling, browser like headers), streamed downloads with progress logging
  • Geoprocessing: Feature layer selection and dissolve for clip boundaries, field calculation, clip, dissolve by class, feature class export to geodatabase
  • Scope flexibility: Statewide, ODOT district, county, and multi county processing from a single tool

Outcome

Floodplain status isn't just one input among many in this pipeline, it's the input every downstream terrain classification defers to. A tool that quietly downloaded stale or corrupted flood data would propagate that error into every parcel classification built on top of it, with no obvious symptom until someone caught it much later.

  • The download logic actively defends against the specific ways this network and this data source fail, rather than assuming a clean connection and a well behaved server.
  • Self checking QA thresholds flag suspicious output (no features, no floodplain polygons, unusually high floodplain coverage) automatically, instead of relying on someone to notice downstream.
  • Local caching means the several hundred megabyte statewide download only has to happen once, not on every run.

That risk gets caught at the source instead of discovered several stages downstream, in a pipeline where floodplain status decides classification outcomes for every parcel in the state.
